MY PERSPECTIVE

What makes a systems problem beautiful?

The most interesting improvements often begin with asking where complexity is actually worth paying for.

What draws me to systems is the discipline of choosing a useful abstraction and making its tradeoffs explicit. A good design isn't simply more accurate, faster, or more sophisticated. It is one that knows which constraints matter, and where an extra layer of intelligence creates measurable value.

01

Formulate the right problem.

Define the bottleneck before choosing the technique. A better framing can matter more than a more complicated solution.

02

Optimize across competing objectives.

Latency, accuracy, throughput, reliability, and cost belong in the same conversation — not in separate charts.

03

Respect the hardware.

Cache locality, memory bandwidth, data movement, and parallelism often determine whether an elegant algorithm wins in practice.

04

Design for change.

Useful systems should remain robust as workloads, data distributions, and operating conditions evolve.

My recurring question: where can learning complement the parts of a system that are already predictable, efficient, and well understood?

AN OPEN NOTEBOOK

Questions worth exploring.

Some are concrete hypotheses; others are starting points for deeper reading.

01 / DATA SYSTEMSQUESTION

Could a learned index coexist with a B-tree instead of replacing it?

Keep cache-friendly upper levels that already work well; use a small learned component only where deeper traversal or cache misses are expensive. Could a hybrid improve tail latency without creating unacceptable update, memory, or correctness costs?

Learned indexes · Cache locality↗
02 / GPU SYSTEMSQUESTION

When should inference optimize for energy rather than maximum throughput?

Batching improves utilization but may increase waiting time. How should a serving system choose between tokens per second, time to first token, joules per token, and tail latency as demand changes?

LLM inference · Scheduling↗
03 / PARALLELISMQUESTION

When is a single-threaded design better?

Parallelism adds coordination, synchronization, and data movement. Could a simpler serial path outperform a parallel approach for latency-sensitive or cache-resident workloads? How do we identify the crossover point?

Concurrency · Performance↗
04 / COMPILERSQUESTION

Can compilers learn which optimization is worth trying?

Rather than replacing correctness-preserving compiler transformations, could a learned cost model prioritize promising schedules, kernel configurations, or memory layouts — with measurement and validation in the loop?

Autotuning · CUDA · Compilers↗
05 / ADAPTIVE SYSTEMSQUESTION

How much adaptivity is actually useful?

Adaptive policies can chase noisy workload signals. When is a stable heuristic the better system? What monitoring and fallback guarantees would make learning-driven decisions safe to deploy?

Control loops · Robustness↗
06 / HARDWARE–SOFTWAREQUESTION

What would a more programmable accelerator enable?

Where should flexibility live: in hardware, the compiler, or runtime software? I'm interested in the boundary between specialized data paths and programmable control for emerging workloads.

Accelerators · Co-design↗
